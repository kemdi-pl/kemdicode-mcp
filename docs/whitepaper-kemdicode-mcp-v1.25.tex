\section{Abstract}

KemdiCode MCP Server is an open-source implementation of the Model Context Protocol (MCP) that provides 142 specialized tools across 23 categories for AI-assisted software engineering. The server integrates with multiple IDE clients (Claude Code, Cursor, KiroCode, RooCode) via a stateful HTTP transport layer with Server-Sent Events (SSE). Key innovations include a 3-layer bus architecture for distributed multi-cluster communication, a persistent cognition system enabling AI self-awareness across sessions, multi-agent coordination through Redis-backed shared state, and support for 8 LLM providers with intelligent routing and structured output. This paper describes the architecture, design decisions, and implementation details of version 1.25.0.

\section{Introduction}

\subsection{Motivation}

Modern AI-assisted development tools require deep integration between Large Language Models and the developer's working environment. The Model Context Protocol~(MCP)~\cite{mcp2024}, introduced by Anthropic, standardizes the interface between AI clients and tool servers. However, reference implementations typically provide a narrow set of tools with limited state management.

KemdiCode MCP Server extends the MCP paradigm with:

\begin{itemize}[nosep]
  \item \textbf{Comprehensive tooling} --- 142 tools covering the full software engineering lifecycle.
  \item \textbf{Persistent cognition} --- AI agents retain decision history, confidence calibration, error patterns, and mental models across sessions.
  \item \textbf{Distributed execution} --- A 3-layer bus enables multi-cluster LLM orchestration with quality-driven aggregation.
  \item \textbf{Multi-agent coordination} --- Redis-backed kanban boards, workspaces, agent registration, and message passing.
  \item \textbf{Provider-agnostic LLM routing} --- 8 providers with fallback chains, cost optimization, and structured output via Zod schemas.
\end{itemize}

\subsection{Design Principles}

\begin{enumerate}[nosep]
  \item \textbf{Zero-friction integration.} Every MCP-compatible client works without modification.
  \item \textbf{Lazy initialization.} Tool schemas and provider connections load on demand.
  \item \textbf{Fail-safe defaults.} Subsystems degrade gracefully when Redis or LLM providers are unavailable.
  \item \textbf{Anti-amplification.} Bus bridges enforce hop limits, deduplication, and source guards to prevent feedback loops.
  \item \textbf{Runtime reconfiguration.} Providers, models, and tool availability can change without server restart.
\end{enumerate}

\subsection{Transport Layer}

The server communicates via JSON-RPC~2.0~\cite{jsonrpc2} over HTTP, following the MCP specification~\cite{mcpspec2025}. The server exposes the following endpoints:

\begin{table}[htbp]
\centering
\begin{tabularx}{0.85\textwidth}{llX}
\toprule
\textbf{Method} & \textbf{Path} & \textbf{Purpose} \\
\midrule
\texttt{GET}  & \texttt{/sse}              & SSE stream for server notifications \\
\texttt{POST} & \texttt{/message}          & JSON-RPC tool invocations \\
\texttt{GET}  & \texttt{/stream/:id}       & Per-request execution stream \\
\texttt{GET}  & \texttt{/health}           & Server health and uptime \\
\texttt{GET}  & \texttt{/tools}            & Tool listing with schemas \\
\texttt{GET}  & \texttt{/mcp}              & Streamable HTTP MCP endpoint \\
\bottomrule
\end{tabularx}
\caption{HTTP endpoints.}
\end{table}

Each connected client receives its own session with isolated working directory, SSE keep-alive, and automatic session ID generation. Session state persists in Redis, enabling recovery after disconnection.

\subsection{Tool Registry}

The tool registry manages 142 tools through a unified \texttt{UnifiedTool} interface:

\begin{itemize}[nosep]
  \item \textbf{Zod schemas} --- Every tool defines its input schema using Zod~\cite{zod}. Schemas are converted to JSON Schema for the MCP protocol, with special handling for \texttt{discriminatedUnion} types (flattened into merged object schemas).
  \item \textbf{Annotations} --- MCP-level hints (\texttt{readOnlyHint}, \texttt{destructiveHint}, \texttt{openWorldHint}) inform clients about tool behavior.
  \item \textbf{Lazy loading} --- Tool implementations load on first invocation. A background warmup phase pre-loads all schemas after server start and emits \texttt{tools/list\_changed} notifications.
  \item \textbf{Availability checking} --- Tools report their health status with soft/force modes and suggest fallback alternatives.
\end{itemize}

\subsection{L3: ClusterBus}

The ClusterBus enables inter-cluster communication over Redis Pub/Sub~\cite{redis}. It supports 12 signal types grouped into four namespaces:

\begin{table}[htbp]
\centering
\begin{tabularx}{0.9\textwidth}{lX}
\toprule
\textbf{Namespace} & \textbf{Signal Types} \\
\midrule
\texttt{llm:*}      & \texttt{request}, \texttt{result}, \texttt{stream-chunk}, \texttt{error} \\
\texttt{cluster:*}   & \texttt{join}, \texttt{leave}, \texttt{heartbeat} \\
\texttt{data:*}      & \texttt{broadcast}, \texttt{unicast} \\
\texttt{control:*}   & \texttt{pause}, \texttt{resume}, \texttt{config} \\
\bottomrule
\end{tabularx}
\caption{ClusterBus signal types.}
\end{table}

Three send modes are supported: \textbf{unicast} (target a specific node), \textbf{broadcast} (all nodes), and \textbf{routed} (via MetaRouter tag-based rules with AND/OR logic). The \texttt{SignalFlowController} provides backpressure, rate limiting, priority filtering, circuit breaking, bloom filter deduplication, and HMAC authentication.

\subsection{L2: DataFlowBus}

The DataFlowBus provides 12 typed channels with Zod-validated payloads for inter-module communication:

\begin{itemize}[nosep]
  \item \textbf{AI channels:} \texttt{ai:completion}, \texttt{ai:structured}, \texttt{ai:research}
  \item \textbf{Kanban channels:} \texttt{kanban:task-change}, \texttt{kanban:complexity}
  \item \textbf{Cognition channels:} \texttt{cognition:decision}, \texttt{cognition:intent}, \texttt{cognition:error}
  \item \textbf{Agent channels:} \texttt{agent:status}, \texttt{agent:message}
  \item \textbf{System channels:} \texttt{system:health}, \texttt{system:config}
\end{itemize}

Each message is wrapped in a \texttt{DataFlowEnvelope} carrying metadata: correlation ID, schema version, priority (0--3), TTL, source/target filters, session ID, and agent ID.

\subsection{L1: GlobalEventBus}

The GlobalEventBus is an in-process singleton with namespaced events following the pattern \texttt{module:category:action}. Handlers execute asynchronously via \texttt{queueMicrotask} with configurable priority. A maximum chain depth of~8 prevents cascading event storms. The Redis bridge propagates events across sessions with two-retry backoff and capped history.

\subsection{Anti-Amplification Guards}

Bridges between layers employ four mechanisms to prevent feedback loops:

\begin{table}[htbp]
\centering
\begin{tabularx}{0.9\textwidth}{llX}
\toprule
\textbf{Guard} & \textbf{Location} & \textbf{Mechanism} \\
\midrule
Hop limit      & bridges.ts      & \texttt{MAX\_BRIDGE\_HOPS = 5}; signals carry \texttt{\_bridgeHops} counter \\
Source prefix   & bridges.ts      & Skip messages with \texttt{source.startsWith("cluster:")} \\
Dedup          & bus.ts          & ClusterBus: seen set (5000+); DataFlowBus: message ID set \\
Chain depth     & global-bus.ts   & \texttt{MAX\_EVENT\_CHAIN\_DEPTH = 8} on nested emits \\
\bottomrule
\end{tabularx}
\caption{Anti-amplification guards.}
\end{table}

\subsection{PassController}

The PassController governs multi-pass LLM execution within a single cluster:

\begin{itemize}[nosep]
  \item \texttt{min-passes} --- the LLM self-assesses task complexity and declares a minimum pass count (capped to \texttt{maxPasses} budget), with early-stop on quality.
  \item \texttt{quality-target} --- iterates until quality $\geq$ threshold or budget exhaustion.
  \item \texttt{fixed} --- skips assessment, executes exactly $N$ passes.
\end{itemize}

\subsection{Store Descriptions}

\begin{description}[style=nextline, font=\normalfont\bfseries]
  \item[DecisionJournal] Records decisions with options, reasoning, and outcome tracking. Supports retrospective evaluation.
  \item[ConfidenceTracker] Maintains calibrated confidence scores (0--1) per domain with trend analysis.
  \item[IntentTracker] Hierarchical goal tracking with mission, sub-goals, and drift detection.
  \item[ErrorPatternDB] Cross-session error database. Matches symptoms to known patterns and suggests fixes.
  \item[SelfCritiqueStore] Post-session reflection producing lessons learned. Supports check-application queries.
  \item[MentalModelStore] Component-relationship maps for system architecture with dependency chains and invariant checks.
  \item[HandoffStore] Auto-enriched session snapshots for structured context transfer between agents.
  \item[ContextBudgetManager] Token estimation for context windows with trim suggestions.
  \item[AmbientLearner] Silent background knowledge gathering: tool usage sequences, file relationships, time patterns.
  \item[AgentRankStore] Composite scoring system with tiers from bronze to diamond, with temporal decay.
\end{description}

\subsection{Reactive Event Handlers}

The cognition system reacts to events via 9 handlers on the GlobalEventBus:

\begin{enumerate}[nosep]
  \item \texttt{decision:recorded} $\to$ auto-create confidence record + cross-link.
  \item \texttt{confidence:low} $\to$ check intent drift.
  \item \texttt{error:recorded} $\to$ scan recent decisions for causal links.
  \item \texttt{error:matched} $\to$ log known fix suggestion.
  \item \texttt{critique:lesson-learned} $\to$ link to error patterns.
  \item \texttt{intent:drifted} $\to$ trigger self-critique.
  \item \texttt{handoff:created} $\to$ link mental models.
  \item \texttt{model:stale} $\to$ flag affected decisions and intents.
  \item \texttt{confidence:outcome} $\to$ propagate to linked decisions.
\end{enumerate}

\section{Security}

\subsection{Multi-Party Computation}

KemdiCode includes a Shamir's Secret Sharing~\cite{shamir1979} implementation for distributed secret management:

\begin{enumerate}[nosep]
  \item \texttt{mpc-split} --- Split a secret into $n$ shares with threshold $t$.
  \item \texttt{mpc-distribute} --- Distribute shares to agents via encrypted Redis channels.
  \item \texttt{mpc-reconstruct} --- Reconstruct the secret from $\geq t$ shares.
  \item \texttt{mpc-status} --- Monitor share distribution and reconstruction state.
\end{enumerate}

\subsection{Input Validation}

\begin{itemize}[nosep]
  \item All tool inputs validated via Zod schemas before execution.
  \item File paths undergo traversal protection (\texttt{validatePathSafe()}).
  \item Redis JSON parsing employs prototype pollution protection, blocking dangerous keys such as \texttt{\_\_proto\_\_} and \texttt{constructor}.
  \item ClusterBus signals authenticated via HMAC.
  \item MetaRouter regex patterns capped at 200 characters to prevent ReDoS.
\end{itemize}

\section{Knowledge Graph}

The Loci subsystem implements a knowledge graph for error-to-solution pathfinding:

\begin{itemize}[nosep]
  \item \textbf{graph-query} --- traverse nodes and edges in the knowledge graph.
  \item \textbf{graph-find-path} --- find shortest path between two concepts (e.g., error symptom to fix).
  \item \textbf{loci-recall} --- retrieve ambient learning insights.
  \item \textbf{sequence-recommend} --- suggest next tool invocation based on historical usage patterns.
\end{itemize}

The graph is stored in Redis with bidirectional edges, enabling both forward (symptom $\to$ cause $\to$ fix) and reverse (fix $\to$ where applied) traversals.

\section{Recursive Tool Invocation}

The recursive invocation system allows tools to call other tools, enabling autonomous agent loops:

\begin{itemize}[nosep]
  \item \textbf{invoke-tool} --- Call any registered tool with arguments, respecting depth limits.
  \item \textbf{invoke-batch} --- Execute multiple tool calls in parallel with concurrency control.
  \item \textbf{agent-orchestrate} --- Autonomous loop: plan $\to$ execute $\to$ evaluate $\to$ repeat.
  \item \textbf{pipeline} --- Define sequential/parallel tool chains with data passing between stages.
\end{itemize}

Safety constraints include configurable maximum recursion depth, per-invocation timeout, and invocation logging for auditability.

\section{Performance Considerations}

\begin{itemize}[nosep]
  \item \textbf{Lazy schema loading} --- Tool schemas load on first invocation; background warmup runs after server start without blocking client connections.
  \item \textbf{O(1) unsubscribe} --- Both DataFlowBus and HealthMonitor use \texttt{Map}-based subscription tracking for constant-time cleanup.
  \item \textbf{Circuit breakers} --- SignalFlowController implements circuit breaking to prevent cascade failures in the cluster bus.
  \item \textbf{Bloom filter deduplication} --- ClusterBus uses a bloom filter for probabilistic dedup, with a secondary seen-set for exactness.
  \item \textbf{Backpressure} --- Signal flow control with queue depth monitoring, buffer/drop policies, and priority-based filtering.
  \item \textbf{Idle cleanup} --- DataFlowBus subscriptions expire after 60 minutes of inactivity; HealthMonitor prunes stale nodes automatically.
\end{itemize}

\section{Conclusion}

KemdiCode MCP Server v1.25.0 demonstrates that the Model Context Protocol can serve as a foundation for comprehensive AI-assisted software engineering. By combining 142 specialized tools, a 3-layer distributed bus architecture, persistent cognition, and multi-provider LLM orchestration, the server transforms MCP from a simple tool-calling interface into a full-featured AI development platform.

The architecture prioritizes safety through anti-amplification guards, input validation, HMAC authentication, and prototype pollution protection. Lazy initialization and runtime reconfiguration ensure the server remains responsive under varying workloads and configurations.

The system draws on recent advances in LLM-based multi-agent systems~\cite{li2024multiagent,guo2024ijcai} for its coordination architecture.

Future work includes expanding the knowledge graph with cross-project learning, adding WebSocket transport support, and deepening the reinforcement learning subsystem for autonomous tool selection optimization.
